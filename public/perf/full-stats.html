Conclusion

    Possible next steps

    Candidates from profiling 7.13.1. None of them is scheduled yet.

    Where the remaining freeze comes from: on facebook.com, NordPass adds one freeze of about 100 ms while the page opens. About half of it is the browser just reading NordPass code, and the browser does this again on every page load. The rest is NordPass setting itself up. Finding the login form is not part of the freeze. On pages with many frames, every extra frame then costs about 25 ms more of set-up.

    • Load the pop-up code only when a pop-up is needed. The autofill icon and pop-ups code (3.3 MB) loads into every page and frame, although most frames never show a pop-up. It is about half of that 100 ms freeze and most of the memory per frame. It is the biggest remaining win, but also a larger change: Chrome, Firefox and Safari handle this differently, so it needs a design first.
    • Postpone set-up work that only the pop-ups need. Today every frame prepares translations, styling helpers and data checks before any pop-up exists. Preparing them the first time a pop-up opens is a smaller change that can come before the one above.
    • Set up form recognition only in frames that have a form field. Form recognition prepares itself in every frame, about 14 ms each, even in frames with nothing to fill. Pages full of widgets and ads would get most of that back.
    • Include only the UI components NordPass uses. The shared component library is bundled in full into the pop-up code today. Less code means less for the browser to read on every page load, and it makes every part of NordPass lighter, not only autofill.
